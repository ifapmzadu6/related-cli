# Measurements

Measured on 2026-05-24 JST, with the Codegraph/token comparison and Codex
with/without smoke test rechecked on 2026-05-25 JST. The editing-agent A/B
evaluation was added on 2026-08-16 JST. These are local measurements, so use
them as directional evidence rather than universal claims. Raw VS Code output
was generated by:

```sh
scripts/compare.sh /tmp/related-vscode
```

The raw report was written to `/tmp/related-compare/summary.md`.

## Compared Axes

The empirical comparisons cover:

- ranking method: `pagerank`, `direct`, `path`, `hot`
- top-K cutoff: `5`, `10`, `20`
- training history window: `200`, `500`, `1000` commits
- large-commit filter: `20`, `80`, `200` files per commit
- on-demand target-history window: `200`, `1000`, and a rejected `5000` probe
- on-demand backend latency: Git full-diff, `git-diff-tree`, `gix` hybrid, and
  `git-rev-list`
- repository variation: `microsoft/vscode`, local `../codex`, local `../too_tired_to_type`

Baselines:

- `path`: content-blind path/name similarity. This approximates "nearby by file
  naming" without reading contents.
- `hot`: globally frequently changed files. This checks whether `related` is
  merely returning popular files.

## Changed-set omission audit holdout

Added on 2026-08-30 JST. `related eval --task audit` uses a chronological
leave-one-out task: for every eligible held-out multi-file commit, one
history-known file is hidden and the remaining known files become the changed
set. The evaluator checks whether `related audit` recovers the omitted file.
Training commits are strictly older than test commits.

Default-confidence runs used `--top 5 --min-confidence medium`:

| repository | test/train | eligible tasks | mode | hit@5 | MRR | avg results | avg false positives | abstention |
|---|---:|---:|---|---:|---:|---:|---:|---:|
| `related-cli` | 10/30 | 60 | direct | 0.5500 | 0.4808 | 4.60 | 4.05 | 0.0000 |
| `related-cli` | 10/30 | 60 | pagerank | 0.5833 | 0.4875 | 4.60 | 4.02 | 0.0000 |
| `too_tired_to_type` | 50/200 | 162 | direct | 0.7654 | 0.6905 | 4.36 | 3.60 | 0.0679 |
| `too_tired_to_type` | 50/200 | 162 | pagerank | 0.7531 | 0.6733 | 4.36 | 3.61 | 0.0679 |
| `vscode-edge-devtools` | 50/200 | 145 | direct | 0.6897 | 0.5625 | 4.97 | 4.28 | 0.0000 |
| `vscode-edge-devtools` | 50/200 | 145 | pagerank | 0.6897 | 0.5275 | 4.97 | 4.28 | 0.0000 |

The eligibility accounting excluded 41, 57, and 9 unknown omitted targets,
respectively. It also excluded zero, one, and two known targets whose commits
did not leave enough known seed files.

An unfiltered `--min-confidence low` comparison used the same target-local
candidate graph and compared direct co-change ordering with the path/name
baseline:

| repository | direct hit@5 / MRR | path hit@5 / MRR |
|---|---:|---:|
| `related-cli` | 0.5833 / 0.5267 | 0.7500 / 0.3958 |
| `too_tired_to_type` | 0.8272 / 0.7331 | 0.8210 / 0.6350 |
| `vscode-edge-devtools` | 0.6897 / 0.5625 | 0.4966 / 0.3597 |

Interpretation:

- Changed-set evaluation is now aligned with the proposed pre-PR use case; the
  older single-seed query evaluation did not measure this workflow.
- Direct co-change had better MRR than path ordering in all three runs and
  better hit@5 in two. The small `related-cli` history favored path hit rate,
  so this is not a universal direct-ranking win.
- The medium discovery threshold still averaged 3.60-4.28 false positives and
  abstained rarely. It remains useful for a shortlist, but is intentionally not
  the default CI failure threshold.
- These tasks predict files from historical commits. They do not establish that
  every recovered historical file was semantically required, or that an agent
  will make a better edit after seeing it.

### Confidence calibration and enforcement

Added on 2026-08-30 JST. The evaluator now reports candidate precision and task
coverage separately for low, medium, and high evidence bands. Threshold sweeps
used the same direct-mode chronological holdouts above. An absolute high
boundary of 20 strongest-pair co-changes produced many false candidates in
`vscode-edge-devtools`; 30 removed every high candidate from
`too_tired_to_type`. A boundary of 25 retained signal in both larger histories
and was selected as the conservative cross-repository compromise:

| repository | evaluated tasks | high candidates | correct high candidates | candidate precision | task coverage | hit given high |
|---|---:|---:|---:|---:|---:|---:|
| `related-cli` | 66 | 0 | 0 | n/a | 0.0000 | n/a |
| `too_tired_to_type` | 162 | 13 | 8 | 0.6154 | 0.0802 | 0.6154 |
| `vscode-edge-devtools` | 145 | 48 | 44 | 0.9167 | 0.3310 | 0.9167 |
| combined | 373 | 61 | 52 | 0.8525 | 0.1635 | 0.8525 |

The small repository correctly produced no high findings because its 30-commit
training window cannot establish a 25-occurrence pair. This is deliberate
abstention, not evidence that the repository has no omissions. The 61-candidate
sample is also too small to interpret `high` as a universal probability.

`related audit --fail-on-confidence high` therefore remains explicit and
disabled by default. Normal discovery exits 0, an opted-in finding exits 3 after
writing the complete audit result, and operational or usage errors exit 1.

Warm-ish CLI latency was remeasured on this repository with the rename-aware
release build, the twenty-file `HEAD~1..HEAD` changed set, and 20 sequential
runs per accuracy level:

| accuracy | median | p95 | max |
|---|---:|---:|---:|
| `fast` | 74.26 ms | 77.68 ms | 558.52 ms |
| `exact` | 153.85 ms | 162.14 ms | 163.09 ms |

Both p95 results met the provisional 500 ms local audit budget. The fast maximum
shows that isolated cold or noisy runs can still exceed it; this is not a
cross-machine service-level guarantee.

### Rename-aware target history

Added on 2026-08-30 JST. Exact queries now select target commits with Git
`--follow --find-renames`, expand the selected commits in batches, and
canonicalize the old and new target names into one relationship chain. Exact
audits select target histories in parallel and expand the union of commit hashes
once, which kept the twenty-seed p95 above within the provisional 500 ms budget.

A repository fixture covered two co-change commits before a rename, the rename
commit itself, and one commit after it. Query and audit both returned the
companion with four co-changes and did not return the old target path as a
candidate. A second fixture staged an uncommitted rename after two historical
co-changes; both fast and exact audit attributed the companion to the visible
new path with two co-changes. Fast audit reports
`exact-blob-renames+diff-renames` for that case; exact reports
`git-follow+diff-renames`.

On 2026-08-31 JST, fast pack history gained a bounded, pack-native detector for
committed renames where exactly one path disappears with the same blob that
appears at the new path. It canonicalizes the selected old target back to the
requested current name. If two deleted paths share that blob, it abstains from
following either; content-changing renames remain exact-mode work. The tree
search stops after 20,000 entries to bound pathological repositories.

The two-boundary pure-rename fixture recovered all five co-change commits in
fast graph/direct paths. An ambiguous fixture with two identical deleted sources retained
only the current-path commit in fast mode instead of attaching an arbitrary old
history. On the real `vscode-edge-devtools` R100 rename
`src/host_beta/messageRouter.ts` to `src/host/messageRouter.ts`, fast and exact
returned the same top-five paths and co-change counts. Twenty sequential query
runs measured:

| accuracy | median | p95 | max |
|---|---:|---:|---:|
| `fast` | 34.21 ms | 66.90 ms | 89.82 ms |
| `exact` | 61.34 ms | 74.70 ms | 82.72 ms |

The twenty-file local audit was also rerun after the detector: fast measured
61.85 ms median and 79.02 ms p95; exact measured 114.84 ms median and 122.64 ms
p95. Both remained under the provisional 500 ms warm p95 budget. Fast had one
667.53 ms cold/noisy maximum, consistent with the earlier non-SLA caveat.

### Rename-aware chronological audit evaluation

Added on 2026-08-30 JST. Audit evaluation now parses Git rename status before
the train/test split. Rename chains contained in training are canonicalized to
the path visible at the training boundary. For a test commit that itself
contains a rename, only that commit's destination-to-source mapping is applied,
matching staged-diff audit behavior. A rename from another held-out test commit
is not shared, so the fixed historical holdout does not gain future or
cross-test information.

The direct/medium three-repository rerun produced:

| repository | training renames | current-test renames | evaluated tasks | unknown targets | hit@5 | MRR |
|---|---:|---:|---:|---:|---:|---:|
| `related-cli` | 0 | 0 | 69 | 55 | 0.7101 | 0.5072 |
| `too_tired_to_type` | 8 | 0 | 162 | 57 | 0.7716 | 0.6825 |
| `vscode-edge-devtools` | 25 | 1 | 146 | 8 | 0.7123 | 0.5880 |

Against the preceding path-name evaluation, `too_tired_to_type` recovered one
additional task (125 rather than 124 hits) while MRR moved from 0.6905 to
0.6825. `vscode-edge-devtools` moved from 145 to 146 evaluated tasks, reduced
unknown targets from 9 to 8, and moved from 100 to 104 hits; hit@5 increased
from 0.6897 to 0.7123 and MRR from 0.5625 to 0.5880. This is directional
evidence for correct rename accounting, not a claim that canonicalization
always improves every ranking metric.

The evaluation canonicalizer is intentionally not injected into live fast
queries because its bounded global name-status read would make fast pay much of
exact mode's selection cost. The pack-native exact-blob detector above instead
extends fast while preserving a narrower, explicitly reported contract; exact
mode remains necessary for similarity-based rename tracking.

Reproduction examples:

```sh
related eval --task audit --repo ../too_tired_to_type \
  --test-commits 50 --train-commits 200 --top 5 \
  --modes direct,pagerank --min-confidence medium

related eval --task audit --repo ../vscode-edge-devtools \
  --test-commits 50 --train-commits 200 --top 5 \
  --modes direct,path --min-confidence low
```

## Token Efficiency

The token-efficiency question is different from the ranking-accuracy question.
`related` does not compress source code into a summary; it returns a companion
file shortlist so the agent can avoid opening broad, speculative context.

Measured on `/tmp/related-vscode` at `34059187419`, target
`src/vs/platform/sandbox/common/terminalSandboxEngine.ts`, history since
`2026-05-08T14:03:23-07:00`, `top=10`.

Tokenizer:

```sh
python3 -m venv /tmp/related-token-venv
/tmp/related-token-venv/bin/python -m pip install tiktoken
```

Commands:

```sh
target/release/related query \
  src/vs/platform/sandbox/common/terminalSandboxEngine.ts \
  --repo /tmp/related-vscode \
  --since 2026-05-08T14:03:23-07:00 \
  --mode direct \
  --top 10 > /tmp/related-token-related-text.txt

(
  cd /tmp/related-vscode
```

  files.

### With related-cli vs Without related-cli

For the token-efficiency claim, "with `related-cli`" means the agent receives
the compact co-change shortlist before opening source files. "Without
`related-cli`" is a no-history-shortlist source-reading baseline: the agent
starts by opening the target and then plausible companion files. The companion
rows use the measured `related` top results as a fixed context set so the token
cost is comparable; they are not a separate no-tool discovery algorithm.

| workflow | context sent before choosing files | tokens | ratio vs `related` text |
|---|---|---:|---:|
| with `related-cli` | Compact top-10 co-change shortlist | `231` | baseline |
| with `related-cli` | Top-10 paths only | `170` | `0.7x` |
| without `related-cli` | Target file body only | `8,625` | `37.3x` |
| without `related-cli` | Target + top companion test body | `14,179` | `61.4x` |
| without `related-cli` | Target + top-10 companion bodies | `46,061` | `199.4x` |

This is a `97.3%` reduction versus opening only the target file, `98.4%` versus
opening the target plus the first companion, and `99.5%` versus opening the
target plus all top-10 companion files.

Simple shell probes can be small, so they should not be treated as the same
baseline as source-reading. In the saved scratch outputs for this target,
`rg` import hits were `200` tokens, an `rg -l` path list was `539` tokens, and a
path-limited `git log --name-only` sample was `291` tokens. Those commands are
useful, but they require a lexical query or path-history inspection and do not
rank language-agnostic co-change partners.

### Editing-agent task outcomes

The compact-output measurements above do not establish that forcing the tool
into every editing task reduces total agent cost or improves correctness. A
larger A/B run on 2026-08-16 tested Codex CLI 0.147.0 once per arm on 20 reviewed
historical tasks from `ifapmzadu6/too_tired_to_type` (40 trials total). The
treatment arm had to run `related-cli@0.4.1` before normal exploration; the
control arm could use direct filename and source search but no Git-history or
co-change lookup.

| metric | without `related` | with `related` | treatment difference |
|---|---:|---:|---:|
| target-file success | `19/20` | `19/20` | no change |
| exact-patch success | `2/20` | `2/20` | no change |
| mean file recall | `98.33%` | `98.33%` | no change |
| non-cached input tokens | `1,404,354` | `1,428,622` | `+1.7%` |
| output tokens | `101,559` | `131,858` | `+29.8%` |
| total elapsed time | `4,287.3s` | `6,586.6s` | `+53.6%` |

Trace review found 58 history queries in the 20 treatment runs, including 10
exact repeats. After changing the skill to default to one query, five selected
cases were rerun in both arms. Every treatment run issued exactly one query,
but target-file success remained tied at `5/5`; treatment still used `13.0%`
more non-cached input, `24.4%` more output, and `32.5%` more elapsed time in
aggregate.

The product conclusion is therefore selective: use co-change history when the
companion-file scope is uncertain or as a one-shot pre-commit/pre-PR omission
audit. Do not require it for every editing task, and do not treat the ranking as
an authoritative edit plan. This suite emphasized multi-file work but used one
repository, manually selected tasks, one run per arm, and limited hidden
semantic tests. See the full [20-case evaluation](https://github.com/ifapmzadu6/related-cli/blob/main/experiments/agent-ab/results/2026-08-16-20-case-evaluation.md)
for method, limitations, and reproduction instructions.

### Git History Reader Experiment

An early experiment checked whether reading Git history more directly should
replace Git's own history output. The answer from the VS Code checkout was no
for full-history precomputation, but yes for targeted on-demand variants.

Measured on `/tmp/related-vscode`, `1000` commits, `max-files-per-commit=80`:

| candidate | result | decision |
|---|---:|---|
| experimental `git2` backend | failed after `2.52s` with missing object resolution | Do not adopt |
| `git rev-list \| git diff-tree --stdin` plumbing probe | raw extraction `0.72s`, but emitted only `830 / 1000` commit records | Do not adopt |

The VS Code checkout used for measurement was both shallow and configured as a
promisor remote (`rev-parse --is-shallow-repository=true`,
`remote.origin.promisor=true`). The `git2` experiment tried to diff commit trees
itself and hit missing object errors such as:

```text
object not found - cannot read header for (...); class=Odb; code=NotFound
```

The plumbing probe was faster as a raw command, but it was not equivalent on the
same checkout because it silently stopped producing records at the shallow
boundary. A custom no-library Git object reader would have to implement commit
walking, tree diffs, pack/index lookup, delta application, and partial-clone
fetch semantics just to match what Git already does here. Based on this
measurement, that complexity is not justified yet.

### On-Demand Target History

`related query` builds the needed history graph on demand for the target file.
There is no persistent index path in the CLI. The default history window is the
target file's latest `1000` touching commits, not the repository's latest `1000`
commits.

The current default is `--history-backend pack-fast`. It is a pack-only reader:

1. Read `.git/HEAD`, refs, `.idx`, loose objects, and `.pack` files directly.
2. Memory-map pack files, binary-search pack indexes, inflate packed objects,
   and apply `OFS_DELTA`/`REF_DELTA` when needed.
3. Walk path history by comparing the target path's tree entry against parent
   trees, then expand selected commits with an in-process tree diff.
4. Stop on a latency budget for LLM-tool use: the default cap is `17,500`
   scanned commits, and after the first `1,000` scanned commits it can stop
   once it has seen `256` target hits or `5,000` scanned commits without
   another target hit.

This default is approximate: co-change counts can be lower than an exact
`git log --full-diff` query because the scan is intentionally bounded. The exact
Git backend remains available as `--history-backend git`, and the same pack-only
implementation can run without the latency-bounded cutoff as
`--history-backend pack-scan`.

The latest randomized VS Code run used `/tmp/related-vscode`,
`--max-commits 1000`, `--mode direct`, `--top 5`, and seven randomized-order runs
per variant:

| target | Git exact median | `pack-fast` median | `pack-scan --scan-commits 17500` median | `pack-scan --scan-commits 17500 --jobs 8` median | result quality |
|---|---:|---:|---:|---:|---|
| `package.json` | `0.3695s` | `0.0926s` | not rerun | `0.2007s` | top-5 set matched Git; `pack-fast` top cochanges `146` vs Git `410` |
| `src/vs/editor/common/model/textModel.ts` | `1.5006s` | `0.2406s` | not rerun | `0.2385s` | top-5 set matched Git; `pack-fast` top cochanges `12` vs Git `143` |

Implementation notes from the pack-only path:

- `pack-fast` avoids Git subprocess startup and Git's full path-limited history
  machinery on the hot path.
- Commit messages are read only when evidence is requested; default LLM-tool
  output does not touch commit subjects.
- Cached object/tree lookups avoid cloning inflated pack data, tree entries are
  shared with `Arc`, pack offset caches are keyed by pack number instead of
  path, and packed-only checkouts skip loose-object filesystem probes.
- Inflated object data is stored as `Arc<[u8]>`, so the pack-offset cache and
  object-id cache can share object bytes instead of cloning the data buffer.
- Pack inflate uses `flate2`'s `zlib-rs` backend and `BufRead` over the mmap
  slice. This replaced the earlier `miniz_oxide`/`Cursor` path and produced the
  largest speedup in the current tuning pass.
- Pack mmap handles are shared through `Arc` when `pack-scan --jobs N` forks
  worker stores, avoiding repeated mmap setup for the same pack.
- Tree diffs use the sorted order of Git tree entries to compare parent and
  child trees with a two-pointer scan, avoiding a per-directory HashMap build.
  The comparator follows Git's tree ordering rule for directories.
- Target-path tree lookup also uses Git's sorted tree order to stop scanning
  once the requested component can no longer appear, and copies the 20-byte
  object id only for the matching entry.
- Direct pack queries aggregate co-change scores while expanding selected
  commits, avoiding the intermediate `Commit` list and avoiding date/hash
  formatting except for returned results or requested evidence.
- Direct pack queries reuse changed-file and path-prefix buffers across selected
  commits instead of allocating fresh vectors for every commit.
- Common one-parent commits avoid heap allocation in both parsed commit parent
  storage and path-history follow decisions.
- Parent commit time is carried out of the path-history decision, avoiding a
  second commit-cache lookup just to push the same parent into the walk heap.
- Commit timestamps and timezones are parsed directly from ASCII bytes, and
  commit-header scanning stops once the `committer` line has supplied the time.
- Common Git tree modes use a fast exact-byte match before falling back to the
  generic decimal parser.
- Release builds use thin LTO with one codegen unit. This improved the measured
  query medians and reduced the binary from about `4.7 MiB` to `4.1 MiB` in the
  local build.
- Multiple pack indexes are searched largest-first. Mapping `.idx` files instead
  of reading them was tested and rejected for this workload because random page
  faults made it slower than a warm contiguous read.
- Result-dependent early stopping based on top-K stability was considered and
  rejected as too meta for the tool semantics. The default cutoff is based only
  on traversal budget and target-hit counts; it does not inspect the produced
  ranking. `pack-scan` remains the explicit deeper path.
- Replacing per-tree HashMap lookup with small-tree linear scans was measured
  and rejected because repeated linear scans were slower on the VS Code targets.
- Caching a per-tree name map was also measured and rejected: it added name
  duplication and allocation overhead that outweighed reuse on the VS Code
  `pack-fast` targets.
- Delaying tree-entry mode/id parsing until after a path-component name match
  looked promising, but measured slower on the larger VS Code targets and was
  reverted.
- Pre-sizing parsed tree-entry vectors from object byte size was mixed and was
  rejected because it worsened the package and sandbox targets.
- Pre-sizing the revision-walk `seen` set from the scan budget was rejected
  because the upfront allocation hurt short target histories.
- Splitting the target-path child-entry cache into one map per path component
  improved one deep target but worsened package and sandbox targets, so the
  single keyed cache remains the default.
- Avoiding `String` clone on existing direct-pair HashMap keys with a
  `get_mut`/insert branch was measured and rejected; the extra branch and insert
  path cost outweighed the saved clone on VS Code `package.json`.
- Raising the direct-pair HashMap initial capacity was measured and rejected
  because upfront allocation hurt the smaller and sparse targets.
- Reusing the parent tree id already read during path-history selection was
  measured and rejected. It preserved output, but the VS Code 15-run medians
  were mixed: `pack-fast` changed by `+0.1%`, `+1.1%`, and `+1.9%` on the three
  standard targets, while `pack-scan` variants moved both up and down.
- An ASCII-only path stringification fast path and additional inline hints were
  measured but not adopted because the VS Code medians were mixed and noisier
  than the existing `from_utf8_lossy` path.
- `panic=abort` was measured with thin LTO. It reduced binary size further but
  worsened the `textModel.ts` median in the VS Code run, so it was not adopted
  for speed.
- `strip = "symbols"` reduced binary size further, but the VS Code timing run
  was mixed and did not support adopting it for speed.
- `pack-scan` can parallelize diff expansion with `--jobs N`; this is explicit
  because it helps deep scans in some targets and is neutral or noisy in others.
  The default `pack-fast` path remains single-thread streaming to avoid
  per-thread object-cache duplication on short LLM-tool calls.
- Direct queries cap tree diff expansion once a commit exceeds
  `--max-files-per-commit`, because that commit will be filtered anyway.
- `pack-scan` is useful for exactness experiments but can be slower on files
  whose target changes are sparse deep in history, especially without a
  commit-graph changed-path Bloom filter.

### Direct Git File Reading Feasibility

Directly reading `.git` files can be faster in a narrow case: a full local clone
with a commit-graph that includes changed-path Bloom filters. A reader could use
that Bloom data to skip commits that definitely did not touch the target path,
then read only the selected commit/tree objects. The current VS Code probe clone
does not have that shape:

- `git rev-parse --is-shallow-repository`: `true`
- partial clone filter: `blob:none`
- promisor pack present: yes
- `.git/objects/info/commit-graph`: absent
- packed objects: `1,492,118` across two packs, `314.22 MiB`

The no-library pack reader now implements the necessary subset directly:
revision walking, pack index lookup, pack object decoding, zlib inflate,
`OFS_DELTA`/`REF_DELTA` resolution, commit and tree parsing, path comparison
against parent trees, and full changed-file expansion for selected commits. The
important measurement result is that an unbounded exact pack walk is still not
the best LLM-tool default without changed-path Bloom data: sparse target files
can require walking deep history. The adopted default therefore uses the same
pack reader with a latency-bounded scan cutoff (`pack-fast`), while `pack-scan`
remains available for deeper or exact pack-only experiments.

Before rename following was introduced, the `direct` query path was optimized
to avoid building the full co-change
pair graph. For direct ranking, only target-to-neighbor pairs are needed, so the
implementation computes those pairs directly from history output. This removes
the O(n^2) all-file pair construction from the agent-facing query path. The
then-current `git` direct path streamed compact `git log --no-renames --full-diff`
output directly into scores without first materializing a `Vec<Commit>`. The
`git-diff-tree` and `git-rev-list` direct paths pass raw commit-hash output straight into
`git diff-tree --stdin`, avoiding Rust-side ObjectId parse/stringify work, and
parse the resulting diff-tree output the same way. The default `--evidence 0`
path uses a compact Git pretty format containing only commit time and ISO date;
hash and subject are requested only when evidence is needed.
Direct-mode normalization stores target and neighbor weights in the direct pair
stats rather than a separate per-file map, and the direct parser trusts Git's
normalized `--name-only` output instead of normalizing and de-duplicating every
path line itself. Direct pair maps borrow path keys and `last_seen` dates from
Git output and allocate result strings only for the final retained rows. Final
result ranking uses top-K selection before sorting those retained rows. The
parser also stops processing a commit as soon as the changed-file count exceeds
`--max-files-per-commit`, because that commit will be filtered anyway. When
`--repo` already points at a worktree root, root resolution avoids an extra
`git rev-parse` subprocess. Evidence is still available on demand with
`--evidence N` and through `explain`.

A faster approximate selector was also added as `--history-backend git-rev-list`.
It selects target commits with `git rev-list HEAD -- <target>` and expands them
with the same `git diff-tree --stdin` path. This is not exactly equivalent to
the pre-rename exact
`git log --no-renames --full-diff --diff-filter=ACMRT -- <target>` backend:
co-change counts can differ, but the top companion paths stayed stable in the
probes below.

Takeaways:

- Parallel `gix` expansion is valuable once the target commit set is known, but
  it is not universally faster than Git's own cached path on every target.
- `pack-fast` is now the best default for the agent-facing CLI goal: it is
  pack-only, avoids Git subprocesses in the hot path, and beat Git exact latency
  across the latest randomized VS Code run while preserving the measured top-5
  path set. Counts are intentionally approximate.
- Varying the target confirms the default should not be justified as "always
  fastest." The stronger argument is correctness parity with Git selection and
  better overall behavior across cold-ish and warm-ish runs.
- `git-rev-list` is useful when speed matters more than exact co-change counts.
  It should remain explicit because it cannot apply Git's `--diff-filter=ACMRT`
  during target commit selection.
- Splitting work across multiple Git subprocesses did not reliably improve
  latency; process and object-cache contention often ate the parallelism.
- Pure library traversal is not robust enough as the default on this partial VS
  Code checkout; the adopted pack reader is no-library and handles the measured
  pack/index/delta cases directly.
- The hybrid backend remains useful when explicitly testing Git-library
  expansion: it preserves Git's correctness for target commit selection and gets
  parallel Rust-side diff expansion.

### Persistent Index Removal

Earlier measurements included persistent-index size and cold-load timings. That
path has been removed from the CLI: `query`, `explain`, and `diff` now build the
needed graph on demand for the requested target file or changed files. The
historical accuracy measurements above use the global in-memory evaluation
shape, while normal CLI workflows use a target-local graph and never produce or
consume a saved graph artifact. The newer `--query-shape on-demand` evaluator
exists specifically to measure that target-local shape.

The release binary size was `4.7 MiB` after the pack-only hot-path
optimizations.

## Measurement Caveats

- The accuracy tables in this document were recorded with the global-graph
  evaluator and correspond to `related eval --query-shape global`. They measure
  the predictive value of the history signal, not the exact target-local graph
  used by the shipping query. New evaluations default to `--query-shape
  on-demand` so production-query accuracy can be measured separately.
- The evaluator only scores files that already appear in the training graph.
  New files in held-out commits are counted as skipped unknown seeds.
- `path` is not grep. Grep needs a text query, while this benchmark starts from a
  file path and predicts companion files.
- The performance numbers are CLI-level timings. A resident MCP server would
  likely have much lower query latency by keeping the graph in memory.
- Comparable external tools are not included in this empirical benchmark because
  they require different setup, hosted services, MCP workflows, or source-parsing
  indexes. [COMPARISON.md](COMPARISON.md) records the public feature comparison
  separately.
